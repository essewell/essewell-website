# Portfolio Narrative

Last reviewed 2026-09-24.

## Core professional narrative

Emmett Sewell should be presented as a **systems/software engineer who works across physical and digital layers**, not as a frontend specialist and not as an "AI person" whose main evidence is tool usage.

The strongest through-line is **end-to-end ownership across interfaces**:

- physical hardware and sensors
- embedded computing and communications
- perception and control logic
- systems/software architecture
- databases and security boundaries
- infrastructure and deployment
- product-facing applications
- operational responsibility

The portfolio should make it clear that Emmett is comfortable moving between these layers and translating an operational problem into a working system.

## Primary identity

Use this hierarchy of identity:

1. **Systems Engineering**
2. **Software Architecture / Full-Stack Systems**
3. **Autonomous & Embedded Systems**
4. **Infrastructure / Operations**
5. **AI-enabled engineering workflows**

AI is an implementation-leverage story, not the headline identity.

## Technical differentiators

### 1. Physical-to-software breadth

The Autonomous UAV provides credible evidence that the portfolio is not simply a collection of web applications. The verified source integrates perception, LiDAR sensing, SPI, embedded Linux, and MAVLink control.

### 2. Production software ownership

The MAKE platform demonstrates responsibility beyond feature coding: migration from prototype, data model, permissions/RLS, deployment, security review, QA, documentation, and requirements translation.

### 3. Operational infrastructure

Broadway shows responsibility for systems that a real business depends on day to day, including self-hosted infrastructure, internal systems, physical-security integration, and fleet automation.

### 4. Interface thinking

Across the strongest work, the interesting engineering is often at the boundary:
camera -> embedded compute; sensor -> filtering; compute -> flight controller; business workflow -> data model; roles -> database policies; field operations -> infrastructure.

### 5. Agentic workflow with explicit controls

The public LinkedIn source supports a differentiated development workflow: CLI coding agents, separate reasoning/architecture context, persistent decision logging, a fixed five-stage validation protocol, and independent database-permission auditing. This should be shown as engineering process discipline rather than as AI novelty.

## Target audiences

### Software engineering / platform hiring manager
Should see production ownership, architecture, security boundaries, deployment, testing and full-stack implementation.

### Systems / embedded / robotics engineer
Should see the UAV architecture, sensor/perception/control pipeline, Linux/hardware interfaces and real-world integration constraints.

### Technical founder or engineering lead
Should see unusually broad ownership, ability to translate ambiguous operational requirements, and comfort operating without a large support structure.

### Recruiter / non-specialist
Within 20 seconds should understand:
- Emmett Sewell
- Systems Engineering at SFU
- builds both physical/embedded systems and production software
- flagship UAV + production platform
- not merely a frontend/web portfolio

## What must not dominate

Do not lead with:
- technology logos
- skill percentages
- AI tools/models
- a long biography
- generic "full-stack developer" messaging
- web-design projects
- GitHub activity metrics
- coursework quantity
- every repository
- decorative dashboards/terminal UI

The user should not need to infer the systems-engineering identity from scattered project cards.

## Relationship between professional software and physical engineering

Do not treat these as separate identities.

The narrative is that the same systems thinking appears in both:

- **UAV:** sensors and perception must cross hardware/software interfaces before control decisions become physical motion.
- **MAKE:** operational requirements cross product/data/security/deployment interfaces before they become reliable production software.
- **Broadway:** physical operations, fleet data, infrastructure, and support meet in a system that must keep working in the real world.

That continuity is the portfolio's core story.

## Tone

Factual, technical, restrained.

Preferred:
- concrete nouns
- architecture
- interfaces
- responsibilities
- constraints
- verified technologies
- direct descriptions of what was built

Avoid:
- "passionate"
- "innovative"
- "cutting-edge"
- "visionary"
- "building the future"
- inflated scale or impact claims
- claims that imply sole authorship of team coursework

## Public-safe language for professional work

Use "Internal Project-Management Platform" unless the employer explicitly approves the product name.

State verified architecture and responsibilities, but never expose:
- private source
- schemas/policy logic
- client/project data
- internal screenshots without approval
- proprietary workflow specifics
- unapproved business metrics

## Content priority

The site is successful when the visitor leaves with one coherent impression:

> Emmett can own complex engineered systems across hardware, software, infrastructure, and operations, and can explain the architecture and constraints behind them.

That sentence is an internal narrative test, not necessarily public hero copy.
